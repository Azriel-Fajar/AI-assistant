1. Introduction

POSIX Threads (Pthreads) is the standard thread API on Linux and other Unix systems. A program uses it by including <pthread.h>. Windows does not use Pthreads. It has its own thread API, the Win32 API (CreateThread, WaitForSingleObject, and others). Because of this, the Pthreads example from the lecture cannot be compiled on Windows with Microsoft Visual C++.

The assignment is to convert the example program in two ways:

ProgramThread libraryLanguageRuns on
0_pthread.cPOSIX Threads (original lecture example)CLinux (Windows only through a translation layer)
1_winapi_thread.cWindows API (Win32) threadsCWindows only
2_std_thread.cppC++ standard thread library (std::jthread)C++23Windows and Linux, same code

All three programs do the same job in three steps: (1) the main thread creates one worker thread and passes it the number 1, (2) the main thread waits for the worker to finish, and (3) the main thread prints the value the worker returned (1 × 10 = 10).

1.1 Environment

  • Operating system: Windows 11
  • Compiler: {{gcc}} (MinGW-w64, UCRT64 environment), used as gcc for C and g++ for C++
  • Language standard: C23 (-std=c23) for the C programs, C++23 (-std=c++23) for the C++ program

All outputs in this report are real outputs from running the programs. The script that builds this report compiles every program, runs each one five times, and checks that the worker always returns 10.

1.2 Why C++ and Not C for Program 2

The assignment allows either the C standard thread library (<threads.h>, C11) or the C++ standard thread library. I first tried C. On this compiler, #include <threads.h> fails with fatal error: threads.h: No such file or directory, because the MinGW-w64 C library does not include the C11 threads header. The C++ thread library is part of the compiler itself (libstdc++), so it works on Windows and Linux in the same way. The lecture slides also recommend std::jthread for C++20 and newer, so Program 2 uses C++23 with std::jthread.

3.3 How the Program Works

  1. Line 5: <windows.h> replaces <pthread.h>. The -pthread flag is no longer needed, because the thread functions live in kernel32.dll, which every Windows program already uses.
  2. Line 9, the thread function: CreateThread requires a function of the form DWORD WINAPI f(LPVOID). LPVOID is the Windows name for void*, DWORD is a 32-bit unsigned integer, and WINAPI sets the calling convention that Windows uses to call the function.
  3. Lines 10–11: the same as the original. The argument is cast back to int* and the message is printed.
  4. Lines 15–17: the result is calculated as a DWORD and the thread ends with ExitThread(result), the Win32 version of pthread_exit. The value becomes the thread's exit code, which the operating system keeps inside the thread object.
  5. Line 21: a HANDLE replaces pthread_t. A handle is a reference to a kernel object, in this case the thread object created by Windows.
  6. Line 26, CreateThread: replaces pthread_create. It has six parameters:
    ArgumentParameterMeaning
    NULLSecurity attributesDefault security, and the handle cannot be inherited by child processes
    0Stack sizeUse the default stack size set in the program file
    thread_runnerStart addressThe function the thread runs
    &thread_argParameterThe void* argument given to the function
    0Creation flagsStart running immediately (CREATE_SUSPENDED would create it paused)
    NULLThread IDThe numeric thread ID is not needed here
  7. Lines 27–30: CreateThread returns NULL on failure. Win32 functions report the reason through GetLastError(), not through errno, so perror from the original is replaced by fprintf with the error code.
  8. Line 35, WaitForSingleObject: replaces the waiting part of pthread_join. A thread object becomes signaled when the thread ends. With the timeout INFINITE, the main thread sleeps until that happens, and the function returns WAIT_OBJECT_0.
  9. Line 41, GetExitCodeThread: replaces the second part of pthread_join: it reads the exit code that the worker set on line 17.
  10. Line 47, CloseHandle: releases the handle. Windows deletes the thread object only when the thread has ended and every handle to it is closed. Forgetting this call causes a handle leak. In Pthreads, pthread_join does this cleanup automatically, but in Win32 waiting and cleanup are two separate steps.

3.5 Analysis

  • The output is the same as the original Pthreads program, so the conversion is correct.
  • No malloc and free. In Pthreads, a thread can only return a void*, so the original had to allocate memory, return its address, and free it in main. In Win32, the exit code is a number (DWORD), so a small integer like 10 can be returned directly. This removes the risk of a memory leak.
  • Limitation of the exit code: it is only 32 bits. On 64-bit Windows a pointer is 64 bits, so a pointer cannot be returned this way. To return larger data, the thread should write it into a structure passed through the LPVOID argument. Also, the value 259 should not be used as a result, because GetExitCodeThread uses it as STILL_ACTIVE to mean "the thread is still running".
  • "Hello from the Main Thread!" was printed first in every run. Creating a new thread takes some time, while main continues to its next line right away. This order is not guaranteed: the operating system scheduler decides which thread runs first, so on another machine the worker could print first. Only the last line is guaranteed to be last, because of WaitForSingleObject.
Microsoft's documentation recommends _beginthreadex instead of CreateThread for threads that call the C runtime library (here, printf). The assignment asks for the Windows API thread, so CreateThread is used directly. With the modern Universal C Runtime used by this compiler, the program runs correctly, as the output shows.

4.3 How the Program Works

  1. Lines 5–8: <thread> provides std::jthread, <format> builds the output text, and <functional> provides std::ref.
  2. Line 12, the thread function: unlike Pthreads and Win32, a C++ thread function can have any parameters with real types. Here it takes the thread number as an int and the place to store the result as an int& (a reference). No void* casting is needed, so the compiler can check the types.
  3. Line 13: std::format builds the whole line first and prints it in one call. If the line were printed piece by piece with several <<, pieces from the two threads could get mixed in the same line.
  4. Line 15: the result is written through the reference, directly into the thread_return_val variable of main.
  5. Line 25, creating the std::jthread: replaces pthread_create. The thread starts immediately and runs thread_runner(thread_arg, thread_return_val).
    • By default, std::jthread copies every argument into the new thread. thread_arg is copied, which is safer than the original, where the worker read main's variable through a pointer.
    • std::ref(thread_return_val) wraps the variable so it is passed as a reference instead of a copy. Without std::ref, the worker would write into its own copy and main would never see the result.
    • If the thread cannot be created, the constructor throws a std::system_error exception instead of returning an error code.
  6. Line 30, join(): replaces pthread_join. Main waits until the worker is finished. join() also guarantees that everything the worker wrote is visible to main afterwards, so reading thread_return_val on line 33 is safe. Reading it before join() would be a data race.
  7. Line 35: there is nothing to clean up. There is no heap memory to free and no handle to close. The std::jthread object releases the thread when it is destroyed at the end of main (RAII).

{{output:2_std_thread}}

4.5 Analysis

  • The output is the same as the original program and Program 1, so the conversion is correct.
  • Returning a value: join() returns nothing, so a C++ thread cannot return a value the way pthread_exit does. This program writes the result into a reference instead. Two other standard ways are std::promise/std::future and std::async, which do return a value, but a reference is the simplest for one number.
  • std::jthread vs std::thread: if a std::thread is destroyed without join(), the program crashes with std::terminate. A std::jthread ("joining thread", C++20) calls join() by itself in its destructor, so forgetting it cannot crash the program. join() is still written on line 30 so the waiting is clear and happens before the result is printed.
  • Portability: this file uses only standard C++, so the same code compiles on Linux with g++ -std=c++23 without changes. The compiler connects std::jthread to the operating system's own threads. On Linux it uses Pthreads. On this Windows compiler (thread model posix), it uses winpthreads, which uses Win32 threads underneath.
  • As in Program 1, main printed first in every run, but the order of the first two lines is decided by the scheduler and is not guaranteed.

The three programs give the same output, so both conversions are correct. They also show that the idea of a thread is the same on every system: create a thread, let it run at the same time as main, wait for it with join, and then read its result. Only the API is different. Pthreads and the Windows API are both low-level C APIs, tied to one operating system, that pass data as void* and need manual cleanup. The C++ standard thread library hides those details. It is portable, type-safe, and cleans up by itself, while underneath it still uses the operating system's own threads.

The part that surprised me most was how differently each API returns a value from a thread. Pthreads needs malloc and a pointer, Win32 uses the thread's exit code, and C++ does not return a value from join() at all, so the result has to go through a reference. I also learned that the Win32 version needs CloseHandle, because waiting for a thread and releasing it are two separate steps on Windows, while pthread_join does both.
