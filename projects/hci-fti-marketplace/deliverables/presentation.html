01 · Problem
01 The Problem

The marketplace already exists — in a chat that fights you.

What breaks today
  • Discovery is impossible. Listings vanish up the chat as new messages arrive. No search, no category, no archive.
  • Trust is a guess. No reviews, no track record, no verified identity to tell a reliable seller from a stranger.
  • No structure. Price, condition, location buried in free-text paragraphs you cannot filter.
  • Negotiation is awkward. Haggling happens in public group chat where everyone watches.
The conventions to keep

The group already uses intent tags. The app maps them to a listing_type so every post carries its purpose:

#WTS Want to Sell #WTB Want to Buy #WTT Trade-in #WTBT Barter
Design goal

Keep the social habit students already have. Replace only the parts that fail: search, structure, and trust.

Design implications
  • Discovery is the headline. Search + browse + category filter lead the product — not a nice-to-have.
  • Trust = identity, not just email. Avatar + real name lead the seller row; verified-email is secondary.
  • Required, card-visible fields. Condition + negotiable-price were near-unanimous mandatory listing info.
  • COD-first. Pickup on campus is the primary deal model; money never flows through the app.
  • Gamify with status. Open feedback asked for a leaderboard + reward — badge tiers became the reward.
Plan-correcting insight

We had framed campus-email as the headline trust signal. The data moved it to secondary and elevated profile photo + identity.

02 · Persona
02 The Persona

Who we are designing for.

A
Aufa, 19
FTI student · interested but hasn't transacted yet
Goals
  • Find a used laptop or electronics from someone on campus, fast.
  • Know the seller is real and trustworthy before meeting.
  • Buy and sell without leaving a noisy group chat.
Frustrations
  • "Sulit menemukan penjual/pembeli" — can't find who is selling what.
  • Scared of being scammed by a stranger with no track record.
  • Listings scroll away; no way to search back for them.
Behaviour

Need-based user, not a daily browser. Trusts via profile photo + identity. Wants to read others' reviews first. Mobile-first, electronics-led.

04 · Desktop / Web
04 Desktop & Web

One codebase, every screen size.

Same Flutter code, responsive web
  • The same app, compiled to web. No second frontend — flutter build web is the alternative storefront.
  • Adapts, not stretches. Card grid scales 2 → 6 columns; bottom tabs become a side rail on desktop.
  • Verified at 360 / 768 / 1280 / 1920px before demo.
  • Admin lives here too. A Filament dashboard at /admin is the assignment's "Desktop Application" — full CRUD over every table.
Architecture

One Laravel API + one MySQL DB. App, web, and admin all read and write the same source of truth — no second database, no sync.

04 · Rationale
04 Design Rationale & Consistency

One brand language across three surfaces.

Why these choices
  • Colour. Royal blue + navy read as trustworthy and academic; yellow is the single accent for CTAs and highlights.
  • Layout. Soft rounded cards, pill buttons, bottom-tab nav — the secondhand-marketplace pattern users already know.
  • Type. Fraunces for display warmth, Outfit for clean UI text, JetBrains Mono for labels and data.
  • Shared terms. Listing / Seller / Offer / Transaction mean the same thing in app, web, and admin.
Palette — single source of truth

Cross-platform consistency (graded)

The four brand hex values and shared component vocabulary are defined once and reused everywhere — so the Flutter app, the web build, and the Filament admin feel like one product.
